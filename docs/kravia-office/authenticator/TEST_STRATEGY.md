# KRAVIA Authenticator — test strategy

## Objective

Prove the complete password → enrollment/verification → AAL2 boundary across:

- backend identity/MFA;
- same-origin Office BFF;
- Office/Finance browser UI;
- native Android authenticator;
- native iOS authenticator where a macOS test host is available;
- physical-device acceptance before employee rollout.

## Test layers

### 1. Unit/security tests

Run existing repository tests first.

Authenticator:

```bash
cd Authenticator
npm ci
npx expo install --check
npm run typecheck
npm test
```

Backend:

```bash
cd Backend
python -m pytest backend/tests -q
python scripts/quality_gate.py
```

Frontend:

```bash
cd Frontend
npm ci
npm run lint
npm run typecheck
npm test
npm run build
```

Required unit/security coverage includes:

- RFC 6238 vectors;
- Base32 decoding/normalisation;
- KRAVIA-only QR provisioning;
- invalid issuer rejection;
- HOTP rejection;
- wrong algorithm/digits/period rejection;
- corporate-account validation;
- stored-account validation;
- offline/network boundary;
- screen-capture/security-profile checks;
- TOTP replay rejection;
- database-atomic counter claim;
- invalid-attempt cap and session revocation;
- stale AAL1 token rejection after AAL2 promotion;
- reset/recovery flow.

### 2. Web E2E — Playwright

Use Playwright for KRAVIA Office/Finance web UI only.

Required browser projects:

- Desktop Chromium
- Desktop Firefox
- Desktop WebKit where supported
- mobile browser emulation for at least one Android-class viewport
- mobile browser emulation for at least one iPhone-class viewport

Web scenarios:

1. login page renders without secret leakage;
2. invalid password does not progress to MFA;
3. valid password produces AAL1 and MFA stage;
4. first enrollment renders QR;
5. manual setup key remains hidden until explicitly requested;
6. enrollment response and page are non-cacheable;
7. six-digit-only input validation;
8. invalid TOTP is rejected;
9. accepted TOTP redirects to authorised landing path;
10. a used TOTP cannot be replayed in another Office session;
11. protected route cannot open at AAL1;
12. AAL2 session can open the correct workspace;
13. cross-origin MFA mutation is rejected;
14. role-aware landing path remains correct;
15. logout clears authenticated web state;
16. recovery/reset paths do not bypass fresh MFA enrollment.

Playwright mobile-device emulation is for the **web application**. Do not represent it as native-app testing.

### 3. Native Android E2E — Maestro + Android Emulator

Primary free native-mobile runner: **Maestro CLI**.

Primary free device runtime: **Android Emulator / AVD** from Android Studio.

Use the installable CI-test APK generated by the authenticator workflow or a locally built test package.

Required Maestro flows:

- clean first launch;
- biometric/device-auth lock screen visible;
- enrollment screen accessible only after local authentication;
- QR-scanner screen opens and requests camera only when needed;
- manual enrollment accepts a valid KRAVIA identity/secret;
- invalid issuer/account/provisioning input is rejected;
- current six-digit code renders;
- countdown changes;
- no copy-to-clipboard action exists;
- app backgrounds → returns locked;
- unlock restores only after device authentication;
- clear app data/reinstall → prior account does not silently reappear;
- enrollment removal requires confirmation;
- screenshot/screen-recording protection is manually verified where the automation framework cannot assert the OS security flag directly;
- airplane/offline mode still permits TOTP generation after enrollment.

ADB is permitted for setup and emulator controls.

### 4. Native iOS E2E

On a macOS host with Xcode:

- run the iOS Simulator;
- use Maestro for UI flows where supported;
- test Keychain/reinstall behavior explicitly;
- test Face ID/Touch ID simulation where supported by the simulator;
- verify app-switcher/screen-capture behavior;
- complete one physical-iPhone acceptance run before production rollout.

Do not block Android local validation because an iOS/macOS test host is unavailable. Mark the iOS gate as external/pending instead of fabricating a pass.

### 5. Physical-device acceptance

At least one supported Android phone and one supported iPhone must complete the acceptance checklist in `PHYSICAL_DEVICE_ACCEPTANCE.md` before production employee rollout.

## Free/local-first tooling

Primary stack:

- Playwright — web E2E and browser/mobile-browser emulation.
- Maestro CLI — native mobile UI E2E.
- Android Studio + Android Emulator — Android virtual devices.
- ADB — Android installation/device control.
- Xcode + iOS Simulator — iOS testing on macOS.
- Appium — optional open-source fallback if a required native scenario cannot be expressed reliably in Maestro.

Do not add a paid device farm as a mandatory dependency.

## GitHub Actions usage rule

Testing is local-first.

- Do not add per-commit cloud-device testing.
- Do not add duplicate workflows.
- Do not push repeatedly just to observe CI.
- Run Playwright/Maestro locally first.
- Keep native-cloud/device-farm execution manual unless KRAVIA explicitly approves it.
- Prefer one final commit after the local suite is green.

## Evidence

Each E2E execution should leave:

- machine-readable test results;
- failure screenshots;
- failure video/trace where supported;
- exact tested commit SHA;
- tested APK/app build identity;
- Android/iOS OS version;
- emulator/device model;
- timestamp;
- explicit PASS/FAIL/SKIPPED status.

Never call a skipped platform a pass.
